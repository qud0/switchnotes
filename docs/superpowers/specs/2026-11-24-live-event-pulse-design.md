# Live Event Pulse: Встроенный Syslog & SNMP Trap демон

**Дата:** 2026-11-24  
**Статус:** На согласовании (Design Doc)  
**Автор / Tech Lead:** Senior Product Engineer  

---

## 1. Контекст и Проблема (Intent & The Why)

### Текущая ситуация
Сейчас мониторинг оборудования в SwitchBook работает по **pull-модели** (`server/snmpMonitorDaemon.js` опрашивает коммутаторы по таймеру раз в 8 секунд). 
У этого подхода есть два существенных недостатка:
1. **Задержка реакции (Latency):** Если на объекте перебит магистральный оптоволоконный кабель или рабочий выдернул патч-корд, оператор узнает об этом только при следующем цикле опроса (спустя 8–15 секунд).
2. **Пропуск кратковременных событий (Flapping / Bursts):** Если порт коммутатора «мигает» (link flap из-за плохого контакта или дуплексной коллизии), периодический опрос может попасть в момент, когда линк кратковременно в состоянии UP, и инженер не заметит аномалию.
3. **Отсутствие информации о причинах:** SNMP-опрос возвращает только сухой статус (operStatus: down), но не сообщает причину (loop-protect, bpdu-guard, storm-control, error-disable, power-loss).

### Решение: Live Event Pulse
Переход на реактивную **push-модель** в реальном времени:
1. Коммутаторы **SNR NAG** и **MikroTik RouterOS** настраиваются на отправку системных сообщений (Syslog UDP 514) и SNMP Traps (UDP 162) на адрес сервера SwitchBook.
2. Встроенный демон `server/eventPulseDaemon.js` мгновенно перехватывает пакет, декодирует его формат, сопоставляет IP отправителя с базой коммутаторов и выделяет целевой порт.
3. Событие за доли миллисекунды пушится в Web UI через WebSocket (`/ws/events`), обновляя статус порта на интерактивной панели, всплывающее уведомление и журнал тревог.

## 2. Цели, Не-цели и Анти-цели (Goals, Non-Goals, Anti-Goals)

### Цели (Goals):
1. **Универсальный UDP-приёмник Syslog (RFC 3164 / RFC 5424 / Raw):**
   * Приём пакетов на порт `SYSLOG_PORT` (по умолчанию 514).
   * Автоматический fallback на порт UDP 1514 (с фиксацией статуса в API), если привилегированные порты < 1024 заблокированы ОС (`EACCES`) или заняты (`EADDRINUSE`).
   * Увеличенный буфер приёма сокета `socket.setRecvBufferSize(1024 * 1024)` для предотвращения потерь при burst-нагрузках.
2. **Приёмник SNMP Trap v1/v2c:**
   * Приём трапов на порт `SNMP_TRAP_PORT` (по умолчанию 162, с fallback на 1162).
   * Обработка стандартных OID: `linkDown` (1.3.6.1.6.3.1.1.5.3), `linkUp` (1.3.6.1.6.3.1.1.5.4), `coldStart`, `warmStart`.
3. **Специализированные парсеры для SNR и MikroTik:**
   * **SNR NAG (SNR-OS):** парсинг паттернов `%LINK-3-UPDOWN: Interface GigabitEthernet1/0/X`, `%STP-6-PORT_STATE`, `%SYS-5-CONFIG_I`, `%PORT-5-LOOP_DETECT`. Маппинг нотации `1/0/X` в физический номер порта.
   * **MikroTik RouterOS:** парсинг тем `interface,info`, `stp,info`, `system,error`, `account,info`. Поддержка сырых сообщений без заголовка BSD-syslog (`bsd-syslog=no`).
   * Строгая защита от ReDoS (все регулярные выражения $O(N)$ без катастрофического backtracking).
4. **Link Flap Detection & Memory Cleanup:**
   * Автоматический детектор: если порт меняет состояние (UP ↔ DOWN) более 3 раз за 60 секунд, выставляется статус `critical_flapping`.
   * Кольцевой буфер с авто-очисткой событий старше 60 секунд для исключения утечек памяти.
5. **Защита от шторма событий (Rate Limiting & Storm Protection):**
   * Не более 20 событий/сек от одного коммутатора. При превышении события сворачиваются в агрегированную тревогу *"Коммутатор X: подавлено N сообщений (Syslog Flood)"*.
6. **Real-Time WebSocket вещание (`/ws/events`):**
   * Единый централизованный роутер апгрейда соединений в `server/index.js` (проверка токена до хендшейка).
   * Клиентский хук `useEventPulse` с экспоненциальным реконнектом, heartbeat ping/pong и catch-up синхронизацией.
   * UI Debounce звуковых тревог (не чаще 1 раза в 3 секунды) и группировка тостов при массовых авариях.
7. **Тестирование и эмуляция («One-Click Simulator»):**
   * Возможность прямо из UI нажать «Отправить тестовый Syslog / Trap» (Link Down на порт X), чтобы проверить работу оповещений без физического отключения кабелей.

### Не-цели (Non-Goals):
1. Замена полноценного централизованного хранилища логов (ELK/Graylog/ClickHouse) — SwitchBook хранит последние 500–1000 релевантных событий коммутаторов в оперативной базе.

### Анти-цели (Anti-Goals):
1. Падение основного сервера из-за ошибок биндинга портов (если порт 514/162 занят другой службой ОС — сервер должен продолжать штатную работу, зафиксировав статус ошибки).
2. Забивание браузера лавиной тостов и аудио-штормом при одновременном падении стека портов.
3. Необратимое слепое перетирание постоянного статуса порта в БД по единичному UDP-пакету без последующей SNMP-верификации.

## 4. Детали Реализации

### 4.1. Бэкенд-модули
1. `server/eventPulseDaemon.js`:
   * Класс `EventPulseDaemon`.
   * Создание UDP-сокетов через `dgram.createSocket('udp4')`.
   * Инициализация `snmp.createReceiver` из `net-snmp`.
   * Сопоставление `remoteAddress` пакета с IP коммутаторов в `storage.getSwitches()`.
   * Встроенный генератор тестовых событий `simulateEvent({ switchId, port, type, message })`.
2. `server/index.js`:
   * Интеграция `eventPulseDaemon.init(httpServer, storage)`.
   * WebSocket хендлер для `/ws/events`.
   * REST эндпоинты:
     * `GET /api/events/status` — текущий статус демона (слушаемые порты, число принятых пакетов).
     * `POST /api/events/simulate` — генерация тестового события для отладки.

### 4.2. Фронтенд-компоненты
1. `src/hooks/useEventPulse.js` (или интеграция в `App.jsx`):
   * Автоматическое WebSocket-подключение к `/ws/events` с переподключением при обрыве.
   * Синхронизация списка `networkAlerts` в реальном времени.
2. Обновление лицевой панели портов (`SwitchFaceplate.jsx` / `SwitchDetailView.jsx`):
   * Визуальный индикатор (пульсирующая красная/оранжевая рамка) вокруг порта, по которому за последние 5 минут было критическое событие или флаппинг.
3. Модальное окно `AlertsModal.jsx`:
   * Вкладка «Живой Syslog / Trap монитор».
   * Кнопка «Протестировать событие» (симуляция Link Down на тестовом порту).
